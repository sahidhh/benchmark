## Security Findings (Critical)

### 1. SQL Injection — `UserService.cs`, lines 22, 38, 52, 62
**Severity: Critical**

`GetByEmail`, `UpdateRole`, `DeactivateUser`, and `GetUserById` all use string interpolation to build SQL queries. Every one of these is a textbook SQL injection vector. `email` is user-supplied input from the login and reset-password endpoints.

```cs
$"SELECT id, email, role FROM users WHERE email = '{email}'"  // line 22
$"UPDATE users SET role = '{role}' WHERE id = {userId}"       // line 38
```

Fix: Use `SqlParameter` for all query parameters.

---

### 2. Plaintext Password Comparison — `AuthController.cs`, line 27
**Severity: Critical**

```cs
if (user.PasswordHash != req.Password)
```

The field is named `PasswordHash` but is compared directly to the raw password string. Either passwords are stored in plaintext, or the hash comparison is wrong. Neither is acceptable. A proper hash comparison (e.g., `BCrypt.Verify`) must be used.

---

### 3. Predictable Password Reset Token — `AuthController.cs`, line 48
**Severity: Critical**

```cs
var resetToken = user.Id.ToString();
```

The reset token is the user's integer ID. An attacker can enumerate all user IDs and reset any account's password without knowing the original credentials.

Fix: Use `RandomNumberGenerator` to generate a cryptographically random token, store it with an expiry, and invalidate it after use.

---

### 4. Unauthenticated Admin Endpoint — `AuthController.cs`, line 55
**Severity: Critical**

`ListAllUsers()` has no `[Authorize]` attribute and no manual authorization check. Any caller — authenticated or not — can retrieve the full user list.

Fix: Add `[Authorize(Roles = "Admin")]`.

---

### 5. Refresh Token Not Validated Against Storage — `AuthController.cs`, lines 35–42
**Severity: High**

`Refresh` accepts any parseable JWT and issues a new token without checking whether the refresh token was ever issued, has been revoked, or belongs to an active session. A stolen or forged token grants indefinite access.

Fix: Store issued refresh tokens server-side, validate on use, and delete after rotation.

---

### 6. No Rate Limiting on Login — `AuthController.cs`, line 20
**Severity: High**

The comment acknowledges this. Unlimited login attempts enable brute-force and credential-stuffing attacks.

Fix: Apply middleware-level rate limiting (e.g., `AspNetCoreRateLimit`) or account lockout after N failures.

---

### 7. Timing Side-Channel on Email Enumeration — `AuthController.cs`, lines 23–27
**Severity: Medium**

The early return on unknown email (`return Unauthorized` at line 24) has measurably different latency than the password-check path. An attacker can determine whether an email is registered by measuring response time.

Fix: Always perform the password hash comparison (against a dummy hash) before returning, regardless of whether the user was found.
