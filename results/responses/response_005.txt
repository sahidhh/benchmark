1.  [HIGH] `AuthController.cs`, `Login` method, line 20: **Security - Timing Side-Channel**. The comparison `user.PasswordHash != req.Password` occurs only after a successful email lookup. This creates a timing difference between an invalid email and a valid email with a wrong password, potentially allowing an attacker to enumerate valid email addresses.
    *   **Suggestion**: Use a constant-time comparison for passwords. Always perform a dummy password hash comparison if the user is not found to equalize timing.

2.  [HIGH] `AuthController.cs`, `Login` method, line 17: **Security - No Rate Limiting**. There is no rate limiting on login attempts, making the endpoint vulnerable to brute-force attacks.
    *   **Suggestion**: Implement a robust rate-limiting mechanism (e.g., IP-based, user-based after a certain number of attempts) to prevent brute-force attacks.

3.  [HIGH] `AuthController.cs`, `Refresh` method, line 35: **Security - Insecure Refresh Token Validation**. The refresh token is not validated against a stored refresh token. Any valid-looking JWT is accepted, which means if an access token is compromised, it can be used indefinitely to generate new tokens, even if the user's session should have been revoked.
    *   **Suggestion**: Implement a proper refresh token mechanism where refresh tokens are stored in a secure database, associated with a user, and invalidated upon use or logout. They should also have an expiration and be single-use.

4.  [HIGH] `AuthController.cs`, `ResetPassword` method, line 50: **Security - Predictable Reset Token**. The `resetToken` is simply the `user.Id.ToString()`, which is predictable and not a secure random value. An attacker could easily guess or enumerate reset tokens.
    *   **Suggestion**: Generate a cryptographically secure, random, and time-limited token for password resets. Store this token securely (e.g., hashed) in the database and invalidate it after use or expiration.

5.  [HIGH] `AuthController.cs`, `ListAllUsers` method, line 57: **Security - Missing Authorization**. There is no authorization check, allowing any authenticated (or potentially unauthenticated, depending on other middleware) caller to list all users. This exposes sensitive user data.
    *   **Suggestion**: Implement proper authorization (e.g., using `[Authorize(Roles = "Admin")]` attribute or policy-based authorization) to restrict access to this endpoint to authorized users only.

6.  [HIGH] `UserService.cs`, `GetByEmail` method, line 20: **Security - SQL Injection**. The SQL query `$"SELECT id, email, role FROM users WHERE email = '{email}'"` directly concatenates the `email` parameter, making it vulnerable to SQL injection.
    *   **Suggestion**: Use parameterized queries (e.g., `SqlCommand.Parameters.AddWithValue`) to prevent SQL injection.

7.  [HIGH] `UserService.cs`, `UpdateRole` method, line 33: **Security - SQL Injection**. The SQL query `$"UPDATE users SET role = '{role}' WHERE id = {userId}"` directly concatenates the `role` parameter, making it vulnerable to SQL injection.
    *   **Suggestion**: Use parameterized queries to prevent SQL injection.

8.  [MED] `UserService.cs`, `UpdateRole` method, line 36: **Correctness - No Rowcount Check**. The method silently succeeds even if `userId` doesn't exist, leading to a false sense of success.
    *   **Suggestion**: Check `cmd.ExecuteNonQuery()`'s return value. If it's 0, throw an exception or return a boolean indicating that no user was updated.

9.  [MED] `UserService.cs`, `DeactivateUser` method, line 44: **Performance - Multiple DB Connections**. The `GetUserById` method opens a database connection, and then the `DeactivateUser` method opens a second, separate connection. This is inefficient and unnecessary.
    *   **Suggestion**: Refactor `DeactivateUser` to either pass the existing connection to `GetUserById` or retrieve the user details and then perform the update within a single connection scope. Alternatively, if `GetUserById` is only used for existence checks, a more efficient `UserExists(int userId)` method could be used.

10. [MED] `UserService.cs`, `GetUserById` method, line 54: **Security - SQL Injection**. The SQL query `$"SELECT id, email, role FROM users WHERE id = {userId}"` directly concatenates the `userId` parameter, making it vulnerable to SQL injection if `userId` were not an integer (though less likely in this specific case, it's a bad pattern).
    *   **Suggestion**: Use parameterized queries to prevent SQL injection.

11. [LOW] `UserService.cs`, `GetByEmail` method, line 16: **Design - Synchronous DB Call**.
